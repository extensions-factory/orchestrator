Saved Filters — Design Spec

Status: Draft for human review · Date: 2026-08-01

1. Overview

Support agents repeatedly rebuild the same ticket filters during every shift. Saved Filters lets each agent name a useful filter and restore it in one action, reducing setup time without changing the existing search model.

2. Context & Assumptions

  • The current filter state already serializes to URL query parameters.
  • Saved filters are private to an account in the first release.
  • Existing ticket search permissions remain authoritative.

3. Scope

Goals

  • Save the current ticket filter with a unique name.
  • Apply or delete a saved filter from the ticket list.
  • Keep saved filters synchronized across the user’s sessions.

Non-goals

  • Shared team filters—the permission and ownership model needs separate design.
  • Automatic filter suggestions—there is no measured need yet.

4. User Stories

US-1: Save and restore a ticket filter (Priority: P1)

As a support agent, I want to save my current ticket filter so that I can return to the same work queue immediately.

Acceptance criteria:

  • GIVEN an unsaved filter WHEN the agent provides a unique name THEN the filter appears in Saved Filters.
  • GIVEN a saved filter WHEN the agent selects it THEN the ticket list restores every saved condition.

US-2: Remove a saved filter (Priority: P1)

As a support agent, I want to delete filters I no longer use so that the list stays relevant.

Acceptance criteria:

  • GIVEN a saved filter WHEN the agent confirms deletion THEN it disappears without changing the active ticket results.

5. Approach

Persist each saved filter as a name plus the existing canonical query string. Reuse the current query parser when applying a filter, keeping one source of truth for filter behavior.

Alternatives considered

OptionWhy rejected
Store a second filter JSON schemaDuplicates query parsing and creates migration work.
Browser-only local storageDoes not synchronize across sessions or devices.

6. Design

Architecture

The ticket page calls the Saved Filters API. The API validates ownership and stores the canonical query string. Applying a filter sends that string through the existing ticket-query parser.

Data model

SavedFilter {
  id: string
  userId: string
  name: string
  query: string
  createdAt: timestamp
}

Error handling

  • Duplicate names return a field-level validation error.
  • Invalid legacy query strings remain visible but cannot be applied.
  • Network failures leave the current ticket results unchanged.

7. Testing Strategy

  • API tests cover ownership, duplicate names, persistence, and deletion.
  • UI tests cover save, apply, delete confirmation, and network failure.
  • An end-to-end checkpoint restores a multi-condition filter in a new session.

8. Success Criteria

  • SC-1: An agent restores a five-condition queue in two interactions or fewer.
  • SC-2: Saved-filter operations introduce no new ticket-query implementation.
